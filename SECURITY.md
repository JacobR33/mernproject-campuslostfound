# Security controls and implementation status

Phases 1-9 implement the foundation, authentication, posts/items, image storage, search, claims, finder decisions, notifications, consent-gated real-time chat, lost-post requests, expiry cleanup and the React client. Reporting, admin moderation and account deletion are implemented; TOTP MFA and backup-code management are implemented. Do not connect the legacy prototype to this API or deploy it as an alternative implementation.

## Persistence and expiry strategy

Posts require `expiresAt` and have an expiry index. All post reads and image delivery exclude expired/deleted records before cleanup runs. The resumable worker transactionally removes post/item/claim/conversation/message records and marks uploads for physical deletion. GridFS deletion happens after commit; failed deletion retains the ledger for retry. There is intentionally no TTL index on posts/uploads: TTL would strand sensitive dependencies or chunks. Unattached uploads expire in 24 hours and interrupted writes in one hour. Ledger-less GridFS files and incomplete chunk groups older than a day are reconciled while recent/journaled writes remain intact. Each pass handles up to 50 posts, 50 pending files and 50 orphan groups, so physical deletion is asynchronous and may lag during backlog/outages. Cleanup health must be monitored. Database integration tests exercise this strategy; production index provisioning remains a controlled deployment step. Conversation creation authorization is a service concern; schema participant validation alone does not prove an approved claim exists.

Claims have a unique `(post, claimant)` index and a bounded attempt counter updated transactionally under a common post-row write lock. Notifications are also deleted with their post. Refresh sessions use a separate family collection retaining current and consumed token hashes; the requested user `refreshTokenHashes` array is retained for schema compatibility but is not the session authority. Coordinates are optional longitude/latitude pairs.

Only server-created MongoDB operator objects use `mongoose.trusted`; request objects are never trusted. The global `sanitizeFilter` setting remains enabled. Authorization uses current database state; JWTs contain user/family/version identifiers, not role or email. MFA-enabled accounts require a password and fresh factor at login, and their session families must record successful MFA before HTTP/socket authentication or refresh. The login lockout does not terminate already-authenticated sessions; credential reset, logout or bans do.

Outbox records necessarily contain recoverable delivery material, encrypted at rest using a domain-separated key derived from `MFA_ENCRYPTION_KEY`. User verification/reset token records remain hashed. The mail worker starts with the API, retries failed sends, and deletes successful jobs; SMTP retries can still duplicate mail following a crash after successful delivery. Tokens remain one-use. TTL deletion is asynchronous, so the worker explicitly checks expiry; late-delivered reset mail can already have an expired token and users must request a fresh link. Delivery/queue failures produce generic responses and sanitized operational events; monitor them and use resend/reset recovery. Production SMTP latency is not part of the HTTP response path. Database/cache timing cannot be made perfectly uniform; generic status/body and matching bcrypt cost mitigate the practical enumeration paths without claiming constant-time database access.

The file mailbox contains intentionally delivered plaintext email links and addresses, is Git-ignored, and must never be web-served. File modes are requested, with Windows ACLs managed by the host. Deployment logs must be shipped to a protected durable audit sink; current audit output is structured stdout, not a separate immutable audit database.

MongoDB documents that [GridFS does not support multi-document transactions](https://www.mongodb.com/docs/manual/core/gridfs/). File bytes therefore never participate in post transactions: the upload ledger is created before a GridFS write, attachments are committed transactionally, and deletion is idempotent after commit. Transaction callbacks recreate/load documents on each retry; the helper uses native driver sessions to avoid Mongoose rollback bookkeeping errors with strict nested schemas. The full integration suite tests both rollback and concurrent attachment, edit and cleanup paths.

The HTTP upload limit bounds each buffered file to 5 MiB; admission bounds concurrent decode work to two per process. Sharp's [limitInputPixels](https://sharp.pixelplumbing.com/api-constructor/) adds a decoded-dimension bound, and output is at most 1600×1600. These controls reduce resource abuse without claiming native codec isolation. Keep Sharp/libvips patched and size host memory for decode work. Slow request protection and deployment-level traffic budgets remain part of the final operational review. All images and explicitly supplied coordinates are public once a post is published; metadata stripping cannot hide personal information visible in pixels. The UI explains this boundary. Admin removal uses a separate Phase 7 role-protected route; admins cannot use another user's owner-only endpoint.

The authoritative answers are stored only as salted hashes. Claimants' submitted answer text is a separate required record, stored in plaintext for the finder to review, excluded from default queries/serialization, and returned only through the authorized finder review DTO. It is never copied into notifications, audit logs, search indexes, claimant responses or conversation messages. A retry replaces that text rather than preserving a sensitive answer history; the monotonic count and audit events preserve attempt accounting. The latest text persists until post cleanup. Database administrators/backups can access that plaintext, so protect MongoDB storage and backup access. The React client renders it as text without HTML injection APIs. Tests cover both HTTP JSON/nosniff semantics and literal React rendering of untrusted text.

Matching and mismatching submissions both become pending and notify the finder. This prevents a direct comparison oracle while retaining manual review. Each valid submission counts, including a pending retry; invalid shape/ID sets and failed transactions do not count. The three-attempt allowance is lifetime per database user/post, independent of IP endpoint windows. Approval requires a matching latest submission and explicit finder consent. It reserves the item without asserting physical return; the finder confirms return separately. Automatic competing denials update those claim records without per-user notification fanout; explicit decisions notify the affected claimant. In-app claim notification storage uses visible-page polling; Phase 6 adds real-time conversation messaging.

All externally visible decision effects commit together; transaction retries never emit pre-commit chat events or emails. Post deletion/expiry cleanup includes claim answers, lost requests, notifications, conversations and messages. Unexpired reserved/returned posts retain their approved conversation reference for the participants, while new claims are rejected. Phase 6 exposes only participant-authorized history and consent-gated messaging; lost requests use a separate author-acceptance flow. Finder-review endpoints provide no admin override; moderation uses separate Phase 7 routes.

[Socket.IO documents that WebSockets are not protected by CORS](https://socket.io/docs/v4/handling-cors/); the explicit Origin/CSRF handshake checks are therefore separate from CORS configuration. Authentication middleware runs again for each event, not merely on initial connection. Cookie refresh does not extend an existing socket's original JWT deadline: the user reconnects using the shared browser refresh coordination. Delivery separately rechecks each receiver so a previously joined, logged-out socket receives no new private message. Idle revoked sockets may remain connected until the sweep, but every attempted send/delivery is independently authorized.

The server persists messages before live fanout and uses acknowledgements plus unique message IDs, addressing Socket.IO's default [at-most-once delivery](https://socket.io/docs/v4/delivery-guarantees/). This is not an unconditional exactly-once network guarantee. A commit may outlive a missing ack; retries must preserve the draft UUID/body. History uses per-conversation server sequences and is reloaded on reconnect; UI merging deduplicates repeated messages. There is no server-side offline packet replay buffer and no client automatic send queue. API/network failures do not dump raw errors or packet bodies.

Chat text is plaintext in MongoDB and readable by authorized participants through the application; it is not end-to-end encrypted. Database/backup access remains sensitive. Messages automatically contain no account email, item private details or verification proof, though users can choose their own message text. Logging must not enable raw Socket.IO packet debug output. Same-site trusted HTTPS/WSS, Upgrade forwarding and an exact WebSocket CSP origin are production requirements. Local Vite proxies preserve Origin and use the existing HTTPS setup. The production hosting policy must add the actual `wss://` origin to connect-src; the preview's localhost origin is not a deployment hostname.

Live fanout currently assumes **one Node API process**. MongoDB stores shared history and rate counters, but cross-process live delivery needs an authorized Mongo-compatible adapter before horizontal scaling. This limitation is explicit rather than claiming cluster delivery. High-load/failover testing, cross-engine reconnection behavior and deployment proxy timeout tuning remain final review/operations work. The sender's identity and consent are checked when processing a message; normal in-flight request timing is not claimed to be an atomic network revocation boundary.

Deletion scopes the target to the authenticated account, never a caller-supplied ID. It erases the User and related active records transactionally. Authored Item records and image bytes are queued for the existing cleanup worker (default 60 seconds, bounded batches); tombstones deny access immediately. If deletion fails, the transaction rolls back and the client can explicitly retry. Deleting an approved claimant/requester removes consent references and reopens a surviving reserved post; returned posts keep their returned status. Unrelated users, reports, conversations and messages remain intact. Both participants lose shared conversation history when one account is deleted, as disclosed before confirmation.

Bans revoke authentication and hide content without deleting it. Existing sockets revalidate credentials on every operation/delivery and during the periodic sweep; an in-flight HTTP response/network frame is not claimed to be recallable. Administrator roles and unbanning require a restricted operator workflow, with no role assignment/unban HTTP API or default admin credential. The interface does not expose email lookup or private chat to administrators. Exact account-ID review is supported for moderation of a public author/report; role and name are public identity fields, while ban state is admin-only.

Reports and moderation audits intentionally use database references instead of snapshots of private item content or contact details. Reports on removed/expired posts disappear during post cleanup. Account deletion removes reports authored by the account, reports on its posts, and moderation audit rows directly referencing its user/post IDs. Audit rows referencing resolved report IDs may remain without report text or a live reporter account. Operational security logs can retain pseudonymous account IDs from earlier events; the deletion event itself omits the actor ID. Retention/access policy for these logs, SMTP deliveries and backups is the operator's responsibility. Development file mailboxes must be expired manually and never served. Mail already in flight cannot be recalled; legacy encrypted envelopes without recipient metadata expire within their original 24-hour TTL.

Remaining operational limits: large account deletion transactions and cleanup backlogs need load testing; storage worker failures delay physical erasure; backups need retention and deletion-aware restoration procedures; campus NATs may share IP rate budgets. A banned/unverified account cannot use the normal authenticated deletion endpoint and needs operator-assisted identity verification/deletion. There is no legal-retention or moderation-appeal workflow. These are explicit Phase 9 review/deployment items, not completed controls.

TOTP interoperability follows [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html); tests check the SHA-1 vectors reduced to the configured six-digit output. A used step cannot be accepted again, including when a backup code is used between authenticator attempts. Accepting an adjacent future step can require waiting until a later step before another authenticator attempt. Keep server/device clocks synchronized; a backup code is a one-use alternative and still needs the password.

The frontend always offers the optional code field at sign-in. There is no pre-login MFA-status challenge, temporary login session or password-only cookie for enabled users. MFA-proven refresh families renew normally until their original expiry. Enabling, disabling and replacing codes keep the current browser signed in with fresh cookies; tabs sharing that cookie jar adopt the new session, while independent devices lose their previous families. No externally visible session or code list is emitted before transaction commit. The accepted current-password reset logic and existing database actor fences remain in place.

The existing MFA_ENCRYPTION_KEY is now operationally critical. Separate HKDF keys protect mail, MFA seeds and backup-code digests. Changing or losing the master key without migrating stored envelopes/digests prevents their use. Back it up privately and keep database backups separately access-controlled. Pending fields expire without deleting users. No new secret/configuration variable was introduced; server/.env.example documents the stable-key requirement. Run the existing production index provisioning command for the new pending-expiry index.

MFA secrets and recovery codes are deliberately displayed to their authenticated owner during setup/one-time recovery-code issuance. They are never served through ordinary status/auth/public routes, persisted to browser storage, put in URLs, mailed or logged. Browser test screenshots are taken only after these values have been dismissed; disposable traces may contain fixture setup responses and must stay private. A lost setup response requires starting a new enrollment; a lost confirmation/replacement response requires checking Settings and using the authenticator to replace codes. The API does not retrieve an old backup set.

Limits tracked for Phase 9: MFA enrollment is optional for admins as well as users; TOTP can be phished and provides no WebAuthn-style origin binding; no automated lost-all-factors recovery, trusted-device bypass, SMS or external recovery service exists. Recovery with no authenticator and no backup codes needs an independently verified operator process, not email reset alone. Production clock synchronization, actual authenticator-device scanning and encrypted-key migration/recovery procedures have not been operationally certified. Existing backup/log retention and deployment TLS requirements still apply.
